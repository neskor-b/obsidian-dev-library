# Коментарі мають пояснювати неочевидне з коду

## Контекст

- Джерело: [[01-Sources/books/a-philosophy-of-software-design/A Philosophy of Software Design|A Philosophy of Software Design]] — John Ousterhout.
- Розділ: 13, Comments Should Describe Things that Aren’t Obvious from the Code, секції 13.1–13.9.
- Основа: наданий текст розділу; тези переказано українською. Приклади коду нижче — навчальні адаптації на TypeScript, а не дослівний код автора.

## Головна ідея

Корисний коментар додає знання, яких не видно з коду поруч: точне значення даних, контракт, задум або причини рішення. Він змінює рівень опису: нижчий рівень додає точності, вищий — інтуїції. «Очевидність» слід оцінювати з позиції людини, яка вперше читає код, а не його автора.

^aphsd-ch13-main-idea

Простіше: код показує, **які операції виконуються**, але не завжди пояснює, **що означають дані, що обіцяє метод і чому обрано таке рішення**. Саме ці прогалини заповнює коментар. Наприклад, тип `number` не відповідає на питання, чи таймаут задано в секундах, чи в мілісекундах.

«Нижчий рівень» тут означає **точніше визначення значення**, а не переказ дрібних кроків алгоритму. «Вищий рівень» — **загальний задум**, який допомагає зрозуміти ці кроки.

## Ключові тези

### Домовленості допомагають писати коментарі послідовно

Автор радить прийняти усталений формат засобу документації мови, наприклад Javadoc, Doxygen або godoc. Домовленості визначають і вигляд коментарів, і те, що потрібно документувати: без цього документацію легко пропустити зовсім.

| Категорія | Яке знання передає |
| --- | --- |
| Інтерфейс | Абстракцію класу; поведінку методу, аргументи, результат, побічні ефекти, винятки та передумови. |
| Поля структури даних | Що означає збережене значення та які обмеження для нього діють. |
| Реалізація | Призначення внутрішніх блоків і причини неочевидних рішень. |
| Міжмодульні рішення | Правила й залежності, що охоплюють кілька модулів. |

Пріоритет — описи класів, методів і полів. Автор рекомендує документувати їх систематично; винятки можливі, коли оголошення справді не залишає нічого корисного для пояснення. Внутрішні коментарі потрібні вибірково.

У TypeScript у цих прикладах використовуємо `/** ... */` для контрактів класів і методів та `// ...` для коротких пояснень усередині коду. Важливий не сам вид дужок: команда має домовитися, де читач знайде правила використання, а де — пояснення реалізації.

### Коментар не повинен переказувати сусідній код

Перевірка автора: чи могла б людина написати цей коментар, лише поглянувши на код поруч і не розуміючи його змісту? Якщо так, пояснення, найімовірніше, нічого не додає. Перетворення слів із назви методу на речення — типовий приклад.

Для `textHorizontalPadding = 4` фраза «горизонтальний відступ тексту» повторює назву. Натомість пояснення «порожній простір ліворуч і праворуч від кожного рядка, у пікселях» додає одиниці вимірювання та уточнює обидві сторони.

**Порівняй два варіанти на TypeScript.**

```ts
// Слабко: горизонтальний відступ тексту.
const textHorizontalPadding = 4;
```

```ts
// Порожній простір зліва І справа від кожного рядка, у пікселях.
const textHorizontalPadding = 4;
```

У першому варіанті читач дізнається те саме, що вже прочитав у назві. Другий відповідає на два питання: **у яких одиницях задано 4** і **до яких сторін застосовується значення**. Отже, сумарно обидва відступи займають 8 пікселів. Просто замінити слова синонімами недостатньо — має з’явитися нова інформація.

> [!warning] Red flag: Comment Repeats Code
> Коментар дублює інформацію, яка вже очевидна з сусіднього коду, замість пояснення її значення.

^aphsd-ch13-repeats-code

### Нижчий рівень: точність значення даних

Назва й тип рідко повністю визначають семантику змінної. Коментар до оголошення має пояснити за потреби:

- одиниці вимірювання;
- включення або виключення меж діапазону;
- допустимість і значення `null`;
- відповідальність за звільнення ресурсу;
- інваріанти та значення відсутнього елемента.

«Зрозуміло з коду» тут означає зрозуміло з оголошення поруч, а не після пошуку всіх використань у програмі.

Приклад із розділу: для таблиці статистики довжин рядків потрібно вказати, що ключ — кількість символів **разом із символом нового рядка**, значення — кількість рядків такої довжини, а відсутній ключ означає відсутність відповідних рядків. Слова «ширини та кількість появ» цього не пояснюють.

Змінну варто описувати через те, **що вона представляє**. Для `receivedValidHeartbeat` достатньо визначити: істинне значення означає, що після останнього скидання таймера виборів отримано heartbeat; поле слугує для обміну інформацією між двома потоками. Перелік місць, де поле перемикають, змушує читача самостійно відновлювати цей зміст.

**Приклад: типи однакові, але значення різні.**

```ts
interface ReadOptions {
  /** Індекс першого байта, який входить у діапазон; ціле число >= 0. */
  start: number;

  /** Індекс першого байта ЗА діапазоном; ціле число >= start. */
  end: number;

  /** Час очікування в мілісекундах; null означає чекати без обмеження. */
  timeoutMs: number | null;
}

const options: ReadOptions = { start: 2, end: 5, timeoutMs: null };
// Обрано байти з індексами 2, 3, 4. Байт 5 не входить у діапазон.
```

Назва `timeoutMs` уже передає одиниці, але навіть вона не пояснює значення `null`. Тип `number` також не гарантує цілі невід’ємні індекси: коментар описує вимоги, а перевірку значень за потреби має забезпечити код.

**Приклад: що означають ключ і значення в `Map`.**

```ts
/**
 * Ключ — довжина рядка в кодових одиницях UTF-16, включно з його
 * символами завершення рядка, якщо вони є. Значення — кількість
 * рядків такої довжини; зберігаємо тільки додатні лічильники.
 * Відсутній ключ означає, що рядків такої довжини немає.
 */
const numLinesWithLength = new Map<number, number>();

numLinesWithLength.set("cat\n".length, 2);
```

Запис `4 → 2` означає «два рядки довжиною 4», а не «рядок № 4 має довжину 2». Тут адаптація до TypeScript важлива: `string.length` рахує кодові одиниці UTF-16, тому `"😀".length` дорівнює 2. Не варто обіцяти в коментарі кількість видимих символів, якщо реалізація рахує інакше.

**Приклад: стан замість історії присвоєнь.**

```ts
class FollowerState {
  // Слабко: встановлюється в true в обробнику heartbeat,
  // а в false — у функції скидання таймера.
  receivedValidHeartbeat = false;
}
```

```ts
class FollowerState {
  /** Чи отримано валідний heartbeat після останнього скидання таймера виборів. */
  receivedValidHeartbeat = false;
}
```

Heartbeat — повідомлення, яким лідер підтверджує, що він досі працює. Другий коментар одразу визначає зміст `true`. Не потрібно шукати дві функції й самостійно з’ясовувати, який проміжок часу описує прапорець. Приклад показує лише значення поля, без моделювання потоків із прикладу книги.

### Вищий рівень: інтуїція та задум

Коментар над блоком коду має дати просту ідею, яка пояснює його структуру. Для пошуку відповідного RPC корисний опис — спробувати додати поточний хеш ключа до ще не надісланого запиту потрібному серверу. Перелік перевірок стану та полів лише відтворює умови циклу.

Такий опис також дає критерій для перевірки реалізації: чи справді цей блок виконує заявлений задум? Водночас він не замінює пояснення окремих нетривіальних умов: у прикладі автора перевірка `maxPos` лишається не поясненою загальним коментарем.

Корисно пояснювати і причину входу в блок. Наприклад, частина ключів могла залишитися неопрацьованою через відсутність даних на сервері, збій сервера або брак місця у відповіді; тому їх позначають для повторного призначення новим RPC.

**Спрощений приклад із пакетами запитів.** RPC — виклик операції на іншому сервері. Тут достатньо уявляти пакет ключів, які хочемо надіслати разом.

```ts
interface PendingBatch {
  serverId: string;
  state: "collecting" | "sent";
  keys: string[];
}

function appendToPendingBatch(
  batches: PendingBatch[],
  serverId: string,
  key: string,
): boolean {
  // Об'єднуємо ключі до одного сервера в ще не надісланий пакет,
  // щоб зменшити кількість мережевих запитів.
  const batch = batches.find(candidate =>
    candidate.serverId === serverId &&
    candidate.state === "collecting" &&
    candidate.keys.length < 100
  );

  if (!batch) return false;
  batch.keys.push(key);
  return true;
}
```

Слабкий коментар сказав би: «Знайти елемент, у якого збігається `serverId`, стан `collecting` і менше ніж 100 ключів». Це повторення умов. Корисний коментар дає **задум** — об’єднання запитів — і **причину** — менше мережевих звернень. Після цього зрозуміло, навіщо перевіряти сервер і стан пакета.

Але причина межі `100` досі невідома. У реальному коді її слід пояснити біля відповідної константи: наприклад, якщо це вимога протоколу, так і написати. Загальний задум не пояснює автоматично кожного обмеження. Число тут навчальне; воно не взяте з протоколу RAMCloud.

### Документація інтерфейсу визначає абстракцію

Коментар класу описує загальні можливості, значення одного екземпляра й суттєві обмеження використання. Коментар методу поєднує короткий опис поведінки очима викликача з точним контрактом:

- значення аргументів, їхні обмеження та залежності між ними;
- результат і спеціальні випадки;
- побічні ефекти;
- винятки, які можуть вийти з методу;
- передумови, зокрема потрібний порядок викликів.

Викликач має отримати достатньо знань з оголошення й коментаря, щоб не читати тіло методу. Якщо опис інтерфейсу неможливо відокремити від реалізації, це може вказувати на неглибокий модуль.

> [!warning] Red flag: Implementation Documentation Contaminates Interface
> Документація інтерфейсу містить внутрішні подробиці, які не потрібні для використання модуля.

^aphsd-ch13-interface-contamination

**Приклад `Buffer::copy`.** Контракт визначає початкову позицію, кількість байтів і вимогу до місткості буфера призначення. Результат — фактично скопійована кількість: вона може бути меншою за запитану, а за відсутності перетину повертається нуль. Це поведінка, яку має знати викликач; спосіб обходу внутрішніх структур до контракту не належить.

**Адаптація копіювання байтів на TypeScript.** У цьому прикладі є додаткові перевірки цілих невід’ємних чисел, оскільки TypeScript `number` не відповідає беззнаковому цілому типу з оригіналу.

```ts
/**
 * Копіює діапазон source у dest, починаючи з нульової позиції dest.
 *
 * @param source Буфер, з якого читаємо байти; метод його не змінює.
 * @param offset Індекс першого байта у source; невід'ємне безпечне ціле.
 * @param length Бажана кількість байтів; невід'ємне безпечне ціле.
 * @param dest Буфер місткістю щонайменше length байтів.
 *   Не повинен використовувати той самий ArrayBuffer, що й source.
 * @returns Фактична кількість скопійованих байтів. Якщо діапазон
 *   виходить за кінець source, копіює лише доступну частину.
 *   Якщо offset >= source.length або length === 0, повертає 0.
 * @throws RangeError Якщо offset чи length не відповідають вимогам
 *   або dest замалий — навіть коли source містить менше даних.
 * @throws TypeError Якщо source та dest мають спільний буфер.
 *
 * Побічний ефект: перезаписує перші стільки байтів dest, скільки
 * повертає функція; решта dest залишається без змін.
 */
function copyBytes(
  source: Uint8Array,
  offset: number,
  length: number,
  dest: Uint8Array,
): number {
  if (!Number.isSafeInteger(offset) || offset < 0 ||
      !Number.isSafeInteger(length) || length < 0 ||
      dest.length < length) {
    throw new RangeError("Invalid range or destination capacity");
  }
  if (source.buffer === dest.buffer) {
    throw new TypeError("Source and destination must not share a buffer");
  }

  const count = Math.min(length, Math.max(0, source.length - offset));
  dest.set(source.subarray(offset, offset + count));
  return count;
}

const source = new Uint8Array([10, 20, 30]);
const dest = new Uint8Array(4);
const copied = copyBytes(source, 1, 4, dest);
// copied === 2; dest містить [20, 30, 0, 0].
```

Лише за контрактом можна передбачити результат: від індексу 1 доступні два байти, тому повернеться 2, хоча запитано 4. Вихід за кінець джерела не є помилкою; неправильні аргументи — є. Коментар також попереджає, що функція змінює `dest`. Натомість знати про `subarray()` і `set()` для виклику не потрібно — це спосіб виконання обіцянки.

Для стислості приклад розрахований на звичайні доступні `Uint8Array`: передавання або від’єднання їхніх буферів під час роботи тут не розглядаємо.

**Приклад `IndexLookup`.** Один екземпляр представляє один запит діапазону за індексом. Опис класу може коротко показати спільне використання конструктора, `getNext()` і методів доступу до даних, залишивши детальні правила описам окремих методів.

| Відомість | Чи потрібна користувачеві `IndexLookup`? |
| --- | --- |
| Формат повідомлень до серверів | Ні, це внутрішній протокол. |
| Правило порівняння ключів діапазону | Так, воно визначає, які об’єкти потраплять у результат. |
| Структура індексу на сервері | Ні; її не повинна потребувати навіть реалізація клієнтського класу. |
| Паралельні запити до серверів | Можливо: загальна характеристика продуктивності може бути важливою користувачеві. |
| Механізм відновлення після збою сервера | Ні, якщо відновлення прозоре. Якщо збій видимий застосунку, слід описати його прояви. |

**Приклад `isReady()`.** Значення `true` означає, що наступний `getNext()` не блокуватиметься: доступний об’єкт **або вже досягнуто кінця вибірки**. Крім того, `isReady()` просуває виконання запиту, тому його треба викликати прямо або через `getNext()`. Це необхідні умови використання; внутрішні стани й порядок застосування правил користувачеві не потрібні.

**Чому «готовий» не обов’язково означає «є об’єкт».** Нижче лише оголошення інтерфейсу навчального аналога, без реалізації мережевої взаємодії:

```ts
interface IndexLookup<T> {
  /**
   * Просуває виконання запиту.
   * true означає, що наступний getNext() завершиться без очікування
   * мережі: є готовий об'єкт АБО вибірка вже закінчилася.
   * false означає, що getNext() може потребувати очікування.
   * Для просування запиту треба викликати цей метод або getNext().
   */
  isReady(): boolean;

  /**
   * Просуває запит і повертає наступний об'єкт, за потреби очікуючи
   * його надходження. null означає кінець вибірки.
   * Отриманий об'єкт вилучається з послідовності майбутніх результатів.
   */
  getNext(): Promise<T | null>;
}
```

Сигнатура `isReady(): boolean` не розкриває жодного з двох важливих фактів: кінець вибірки теж є готовим станом, а перевірка ще й виконує роботу. Коментар «перевіряє готовність» залишив би обидва факти прихованими. У TypeScript-адаптації `getNext()` повертає `Promise`: очікування мережі асинхронне; навіть готовий результат залишається результатом через `Promise`.

### Усередині методу пояснюй завдання та причини

Коротким простим методам часто достатньо інтерфейсного коментаря й зрозумілого коду. У довгих методах корисні описи основних фаз і нетривіальних циклів: що виконує блок або одна ітерація, без переказу кожної операції.

Неочевидне виправлення помилки потребує пояснення, чому доданий код необхідний. Якщо подробиці вже добре описані в задачі трекера, можна послатися на неї. Локальна змінна частіше потребує коментаря, коли її використання розкидані по великому фрагменту; близькі використання та вдала назва часто достатні.

**Приклад: чому не застосовуємо запізнілу відповідь.**

```ts
class SearchState {
  /** Номер останнього розпочатого пошуку в цьому екземплярі. */
  private latestRequestId = 0;
  results: string[] = [];

  constructor(
    private readonly fetchResults: (query: string) => Promise<string[]>,
  ) {}

  async search(query: string): Promise<void> {
    const requestId = ++this.latestRequestId;
    const results = await this.fetchResults(query);

    // Старий запит може завершитися після нового. Його відповідь
    // не повинна замінити результати для останнього введеного тексту.
    if (requestId !== this.latestRequestId) return;

    this.results = results;
  }
}
```

Користувач ввів `ca`, а потім `cat`. Якщо відповідь для `cat` прийшла першою, пізніша відповідь для `ca` вже застаріла. Коментар пояснює цю ситуацію й призначення перевірки. Фраза «якщо номери не збігаються, вийти» лише повторила б `if`. Приклад зосереджений на порядку відповідей; обробку помилок запиту тут пропущено.

### Міжмодульні рішення мають бути доступними для пошуку

Спільні правила важливо розміщувати там, куди розробник природно потрапить під час зміни. У RAMCloud додавання коду статусу потребує синхронних змін повідомлень, винятків і мовних прив’язок. Перелік цих змін розміщено наприкінці оголошення `Status`, поруч із місцем додавання нового значення.

Якщо природного центру немає, автор експериментує з файлом `designNotes`: одна секція на тему та короткі посилання з відповідних ділянок коду. Приклад — нейтралізація zombie-серверів, які кластер вважає мертвими, хоча вони ще працюють: їхні читання можуть повертати застарілі дані, а прийняті записи — загубитися після відновлення на інших серверах.

Єдиний опис зменшує дублювання та полегшує пошук через посилання. Компроміс: він віддалений від реалізації, тому його актуальність важче підтримувати. Автор подає це як експериментальний підхід, а не остаточно розв’язану проблему.

**Приклад: правило, яке зачіпає сервер і клієнт.**

```ts
// shared/error-code.ts
export type ErrorCode =
  | "NOT_FOUND"
  | "ACCESS_DENIED";

// Додаючи код помилки, узгодь зміни в:
// 1. server/error-to-http.ts — відповідність HTTP-статусу;
// 2. client/error-message.ts — повідомлення користувачеві;
// 3. tests/error-contract.test.ts — перевірка узгодженості.
// Правила сумісності: docs/design-notes.md, розділ «Коди помилок».
```

Це умовні шляхи навчального проєкту. Сам тип перелічує допустимі значення, але не повідомляє, **які інші частини системи потрібно узгодити**. Коментар стоїть біля місця, куди розробник прийде додавати код помилки. Довге пояснення сумісності зберігається один раз, а з залежних модулів на нього ведуть посилання. Якщо узгодженість можна забезпечити типами або автоматичною перевіркою, це корисно зробити: коментар пояснює правило, але сам його не контролює.

## Практичні правила

1. Визнач, для кого коментар: користувача інтерфейсу чи того, хто змінює реалізацію.
2. Прибери переказ назв і операторів; додай відсутнє значення, умову або причину.
3. Для даних перевір одиниці, межі, `null`, інваріанти й володіння ресурсами.
4. Для методу перевір повноту контракту без читання його тіла; винеси внутрішні подробиці в реалізацію.
5. Для складного блоку сформулюй загальне завдання й поясни неочевидні причини.
6. Для спільного рішення знайди природне місце документації або один опис із посиланнями з усіх залежних місць.
7. Якщо рев’юер не зрозумів код, з’ясуй прогалину й уточни код або коментар. Власне знання реалізації не робить її очевидною для нового читача.

## Важлива цитата

> “comments should describe things that aren’t obvious from the code.”

^aphsd-ch13-quote

Зміст: коментар має передавати знання, яких читач не отримує із сусіднього коду.
