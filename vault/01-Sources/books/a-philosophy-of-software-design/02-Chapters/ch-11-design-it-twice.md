# Проєктуй двічі

## Контекст

- Джерело: [[01-Sources/books/a-philosophy-of-software-design/A Philosophy of Software Design|A Philosophy of Software Design]] — John Ousterhout.
- Розділ: 11, Design it Twice.
- Основа: наданий текст розділу; тези й приклад переказано українською.

## Головна ідея

Для кожного важливого дизайнерського рішення розглянь кілька суттєво різних варіантів, перш ніж обирати один. Порівняння виявляє слабкі місця, які важко помітити в єдиній, на перший погляд вдалій ідеї. Найкраще рішення може бути одним із початкових варіантів, їх поєднанням або новим підходом, підказаним їхніми недоліками.

^aphsd-ch11-main-idea

## Ключові тези

### Порівнюй різні підходи на рівні ескізів

Не потрібно повністю реалізовувати два дизайни або наперед визначати всі можливості кожного. Для інтерфейсу класу достатньо окреслити кілька найважливіших методів і перевірити, як ними користуватиметься інший код.

Що сильніше відрізняються підходи, то більше можна дізнатися з порівняння. Навіть якщо другий варіант здається невдалим, варто продумати його: пояснення його недоліків допомагає точніше зрозуміти переваги першого. «Двічі» не обмежує пошук двома варіантами — якщо обидва незручні, шукай третій.

^aphsd-ch11-alternatives

### Приклад: інтерфейс текстового класу

Клас зберігає текст файлу для графічного редактора. Потрібно визначити, якими операціями він обслуговуватиме решту редактора.

| Підхід | Одиниця роботи | Що мусить робити код редактора |
| --- | --- | --- |
| За рядками тексту | Вставляти, змінювати й видаляти цілі рядки | Самостійно розділяти та з'єднувати рядки для операцій із частиною рядка або виділенням через кілька рядків |
| За символами | Вставляти й видаляти окремі символи | Організовувати цикли для кожної багатосимвольної зміни; окремий виклик на кожен символ також може погіршити продуктивність |
| За діапазонами | Змінювати довільні діапазони символів, зокрема через межі рядків | Передавати потрібний діапазон, залишаючи текстові маніпуляції всередині класу |

Усі три інтерфейси можуть виглядати простими самі по собі. Вирішальна відмінність — скільки додаткової роботи вони нав'язують викликачам. Інтерфейс за діапазонами краще відповідає таким діям редактора, як вирізання та вставлення виділеного тексту.

^aphsd-ch11-text-api

> [!warning] Текстові маніпуляції витікають до викликачів
> Якщо для використання текстового класу вищий рівень мусить сам розділяти, з'єднувати або поелементно обробляти текст, це сигнал переглянути абстракцію. Клас має брати на себе текстові маніпуляції, потрібні для його операцій.

Якщо спершу розглянули лише рядки й символи, їхній спільний недолік підказує третій варіант: операції користувача не обмежуються одним рядком чи символом, отже інтерфейс має підтримувати довільний діапазон.

### Критерії залежать від рівня рішення

Для **інтерфейсу** головний критерій — зручність використання кодом вищого рівня. Додатково порівнюй простоту інтерфейсу, його загальність і те, чи дозволяє він ефективну реалізацію. Мала кількість простих методів сама по собі ще не означає зручний API.

Для **реалізації** головними стають простота та продуктивність. Той самий текстовий клас можна реалізувати через зв'язний список рядків, блоки символів фіксованого розміру або буфер із проміжком (*gap buffer*). Розділ називає ці альтернативи, але не визначає універсального переможця.

Порівняння варіантів корисне також для вибору можливостей користувацького інтерфейсу й поділу системи на великі модулі. Спочатку можна окремо порівняти інтерфейси, потім — способи реалізації обраного інтерфейсу.

^aphsd-ch11-criteria

### Невелика інвестиція перед реалізацією

За оцінкою автора, для невеликого класу розгляд альтернатив може зайняти лише годину-дві порівняно з днями чи тижнями реалізації. Це орієнтир, а не жорсткий ліміт. Для більших модулів дослідження триватиме довше, але зростає й користь кращого рішення.

### Порівняння розвиває дизайнерське судження

Автор описує пастку звички до швидкого успіху: якщо перша ідея раніше давала хороший результат, легко почати вважати перегляд рішення ознакою недостатніх здібностей. Але складність великих програмних систем вимагає перевіряти альтернативи незалежно від досвіду чи інтелекту.

Побудова й порівняння варіантів дають подвійний результат: покращують поточний дизайн і навчають розпізнавати чинники, що роблять наступні рішення кращими або гіршими.

^aphsd-ch11-design-skill

## Практичні правила

1. Для важливого рішення накресли щонайменше два суттєво різні підходи; не витрачай час на повну реалізацію кожного.
2. Для кожного запиши переваги й недоліки. Для API насамперед простеж роботу викликачів на типових операціях.
3. Порівняй зручність, простоту, загальність та можливість ефективної реалізації; для внутрішньої реалізації зосередься на простоті й продуктивності.
4. Якщо всі варіанти мають спільну проблему, використай її як підказку для нового дизайну.
5. Обери найкращий варіант або поєднай корисні риси кількох; будь готовий відмовитися від першої ідеї.

## Важлива цитата

> “Try to pick approaches that are radically different from each other; you’ll learn more that way.”

^aphsd-ch11-quote

Зміст: порівняння принципово різних підходів навчає більше, ніж незначні варіації одного рішення.
