# Приховування інформації та її витік

## Контекст

- Джерело: [[01-Sources/books/a-philosophy-of-software-design/A Philosophy of Software Design|A Philosophy of Software Design]] — John Ousterhout.
- Тип джерела: книга.
- Розділ: 5, Information Hiding (and Leakage), секції 5.1–5.10.
- Основа: наданий уривок; саме зображення 5.1 не надано, приклад пояснено за текстом.

## Головна ідея

Будуйте межі модулів навколо знань і проєктних рішень, які вони можуть приховати. Якщо одне рішення зосереджене всередині модуля, його інтерфейс стає простішим, а зміни рідше поширюються на решту системи. Це основний спосіб створювати глибокі модулі.

^aphsd-ch05-main-idea

## Ключові тези

- **5.1. Приховування інформації:** реалізація містить знання, якого немає в інтерфейсі. Це зменшує когнітивне навантаження та залежності від змінюваних деталей. `private` недостатньо, якщо getters і setters розкривають ці рішення. ^aphsd-ch05-hiding
- **5.2. Витік інформації:** одне рішення відображене в кількох модулях; змінювати доводиться всі. Спільне знання формату може витікати й без видимих ознак в API. ^aphsd-ch05-leakage
- **5.3. Часова декомпозиція:** поділ за порядком операцій часто дублює знання між етапами. Межі варто визначати за тим, що модуль знає, а не коли його викликають. ^aphsd-ch05-temporal
- **5.4–5.5. HTTP-приклад:** отримання запиту та його розбір тісно пов’язані. Об’єднання відповідних класів може приховати більше знань і замінити два обов’язкові виклики одним. Більший клас не автоматично кращий: перевага виникає від кращої межі абстракції.
- **5.6. Параметри:** приховуйте їхнє розташування, декодування й внутрішнє зберігання; повертайте значення, потрібні клієнтові. ^aphsd-ch05-parameters
- **5.7. Типові значення:** звичайний сценарій має працювати без зайвих налаштувань; окреме перевизначення забезпечує часткове приховування. Overexposure змушує всіх вивчати можливості, потрібні небагатьом. ^aphsd-ch05-defaults
- **5.8. Усередині класу:** приватні методи також мають приховувати знання; зменшення кількості місць доступу до поля скорочує внутрішні залежності. ^aphsd-ch05-internal
- **5.9. Межа принципу:** не приховуйте інформацію, необхідну клієнтові. Якщо різні сценарії потребують різних налаштувань і автоматичний вибір недостатній, налаштування мають бути доступними. ^aphsd-ch05-limits
- **5.10. Глибина:** більше прихованих знань за простішим інтерфейсом означає глибший модуль.

## Приклади з розділу

### Читання та розбір HTTP-запиту

У навчальному прикладі читач мусить розібрати `Content-Length`, щоб визначити довжину тіла. Якщо окремий parser повторно розбирає запит, обидва класи знають його формат. Спільний модуль читання й розбору зосереджує це знання та позбавляє клієнта обов’язку координувати два виклики.

### Доступ до параметрів

У прикладі автор пропонує об’єднати параметри з URL та тіла й декодувати їх до повернення клієнтові: `What+a+cute+baby%21` стає `What a cute baby!`. Це опис параметрів у наведеному кодуванні, а не правило для довільного HTTP-тіла.

```java
// Поверхневий API розкриває внутрішню колекцію.
public Map<String, String> getParams() {
    return this.params;
}

// Запропоновані в розділі сигнатури API:
public String getParameter(String name) { ... }
public int getIntParameter(String name) { ... }
```

Перший варіант прив’язує клієнта до представлення, вимагає додаткового звернення до `Map` і дозволяє випадково змінити внутрішній стан. Другий приховує сховище; типізований метод додатково бере на себе перетворення. За контрактом із розділу відсутній параметр або невдала конвертація спричиняє виняток; конкретні типи винятків не наведено. Сигнатури з `...` є ескізом API.

### Типові значення відповіді

У навчальному дизайні бібліотека вже має запит, тому сама може визначити відповідну версію відповіді. Автор також пропонує автоматично задавати `Date`. Аналогічно, автоматична буферизація у прикладі файлового I/O усуває потребу окремо компонувати типовий сценарій.

## Практичні правила

- Перелічіть рішення, від яких залежить модуль, і знайдіть інші місця, де ці рішення повторюються.
- Для витоку розгляньте об’єднання тісно пов’язаного коду або окремий модуль зі справді простим API.
- Перевіряйте, чи нова абстракція приховала знання, а не лише перенесла їх у getters.
- Замінюйте обов’язкову для всіх послідовність дрібних викликів однією змістовною операцією, коли вона відповідає цілісній можливості.
- Відокремлюйте рідкісні налаштування від типового сценарію.
- Залишайте видимими потрібні клієнтові параметри й гарантії.
