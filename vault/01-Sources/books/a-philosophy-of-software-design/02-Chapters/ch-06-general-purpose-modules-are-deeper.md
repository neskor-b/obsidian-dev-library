# Модулі загального призначення є глибшими

## Контекст

- Джерело: [[01-Sources/books/a-philosophy-of-software-design/A Philosophy of Software Design|Нотатка книги]] — John Ousterhout.
- Розділ: 6, General-Purpose Modules are Deeper, секції 6.1–6.6.
- Основа: наданий текст розділу.

## Головна ідея

**Реалізуйте потрібні сьогодні можливості, але описуйте їх через загальні операції, які не прив’язані до одного сценарію використання.** Такий інтерфейс часто має менше методів, краще розділяє відповідальність і спрощує програму вже зараз, навіть якщо повторного використання ніколи не буде.

^aphsd-ch06-main-idea

Інтерфейс тут — доступні операції та правила їх використання. «Загального призначення» означає, що одна операція придатна для кількох задач. Це не вимога наперед реалізувати всі можливі майбутні потреби.

## Ключові тези

### 6.1. Помірна універсальність

Спеціалізований модуль легко прив’язати до сьогоднішньої задачі настільки сильно, що кожен новий сценарій потребуватиме нового методу. Надмірно універсальний модуль може містити непотрібні можливості та ускладнювати звичайне використання.

Компроміс автора: **функціональність визначають поточні потреби, а інтерфейс має підтримувати кілька способів використання**. Критерій успіху — простота поточного коду, а не кількість уявних майбутніх застосувань.

^aphsd-ch06-generality

### 6.2. Як текстовий клас стає залежним від інтерфейсу редактора

У навчальному проєкті редактор мав показувати файл у кількох вікнах та підтримувати багаторівневі undo/redo. Клас тексту відповідав за завантаження, читання, зміну й збереження тексту. Частина студентів додала до нього методи під конкретні дії користувача:

```java
void backspace(Cursor cursor);
void delete(Cursor cursor);
void deleteSelection(Selection selection);
```

Так клас тексту почав знати про клавіші, курсор і виділення. Розробнику доводилося вивчати багато вузьких методів, а нова дія в редакторі могла вимагати змін одразу у двох класах. Це приклад витоку інформації: деталі інтерфейсу користувача потрапили до модуля зберігання тексту.

### 6.3. Кілька загальних операцій замість методів для кожної клавіші

Автор пропонує API, що оперує текстом і позиціями:

```java
void insert(Position position, String newText);
void delete(Position start, Position end);
Position changePosition(Position position, int numChars);
```

`insert` вставляє довільний рядок. `delete` видаляє напіввідкритий діапазон `[start, end)`: початкова позиція входить, кінцева — ні. `changePosition` повертає позицію на задану кількість символів раніше або пізніше та сам обробляє переходи між рядками. Тип `Position` описує місце в тексті без прив’язки до курсора на екрані.

^aphsd-ch06-text-api

Тепер рішення про поведінку клавіш лишається в коді інтерфейсу користувача:

```java
// Delete: видалити символ праворуч від курсора.
text.delete(cursor, text.changePosition(cursor, 1));

// Backspace: видалити символ ліворуч від курсора.
text.delete(text.changePosition(cursor, -1), cursor);
```

Виділення також можна видалити через `delete`, передавши його початкову та кінцеву позиції. Окремий метод `deleteSelection` у класі тексту вже не потрібен.

Виклик трохи довший, зате з нього видно, що саме видаляється. Загалом коду стає менше: одну операцію видалення діапазону використовують у кількох сценаріях замість набору вузьких методів.

> [!note] Межі наведеного прикладу
> Це схематичний API з книги. Уривок не визначає поведінку на початку й у кінці файлу та точне значення «символу». Для робочого API ці правила потрібно уточнити. Вимоги до undo/redo й кількох вікон задають контекст задачі; їхню реалізацію цей приклад не розкриває.

Для пакетної заміни рядків цей самий клас також корисний. Йому може знадобитися пошук:

```java
Position findNext(Position start, String string);
```

Якщо редактор уже підтримує пошук і заміну, така можливість може бути реалізована для поточних потреб. Це приклад повторного використання, а не привід завчасно додавати непотрібний пошук.

### 6.4. Приховуйте внутрішні механізми, залишайте потрібні рішення видимими

Клас тексту має знати, як змінювати текст і обчислювати позиції. Клас інтерфейсу користувача має знати, яку ділянку видалити після натискання Backspace. Завдяки цьому нові дії, що складаються з наявних операцій, можна додавати без зміни текстового API.

Метод `backspace` у текстовому класі — хибна абстракція: він приховує вибір символу від того модуля, якому цей вибір потрібен. Розробник інтерфейсу може все одно піти читати його реалізацію, щоб перевірити поведінку. Явний діапазон у виклику `delete` робить потрібне знання доступним у правильному місці.

^aphsd-ch06-false-abstraction

### 6.5. Три запитання для перевірки API

| Запитання | Що перевірити на практиці |
| --- | --- |
| Який найпростіший інтерфейс покриває поточні потреби? | Чи можна об’єднати вузькі методи без втрати можливостей і без безлічі нових параметрів? |
| У скількох ситуаціях буде корисний метод? | Метод під одну дію — сигнал переглянути дизайн, а не автоматична помилка. |
| Чи легко використовувати API для поточної задачі? | Чи не доводиться клієнтам писати багато допоміжного коду для звичайних операцій? |

^aphsd-ch06-questions

Наприклад, вставлення й видалення лише одного символу дають простий та універсальний API, але змушують клієнта писати цикли для рядків і діапазонів. Це ускладнює редактор і може бути неефективним для великих змін. Тому підтримка діапазонів має бути всередині текстового класу.

^aphsd-ch06-ranges

### 6.6. Висновок автора

Помірно універсальні інтерфейси зазвичай мають менше, але глибших методів. Вони зменшують кількість знань, потрібних клієнтам, і допомагають незалежно розвивати модулі.

## Приклади на TypeScript

Це навчальна адаптація ідей розділу, а не код із книги. Приклади показують контракти та код клієнтів; реалізацію зберігання тексту пропущено.

### 1. Спеціалізований API переносить знання про UI в текстовий модуль

```typescript
type Cursor = { offset: number };
type EditorSelection = { from: number; to: number };

interface EditorSpecificText {
  backspace(cursor: Cursor): void;
  deleteAtCursor(cursor: Cursor): void;
  deleteSelection(selection: EditorSelection): void;
}
```

Усі три методи змінюють текст, але названі й типізовані через дії редактора. Для видалення слова розробник може додати ще один вузький метод, хоча механізм видалення діапазону вже вирішує цю задачу.

### 2. Загальний API описує операції над текстом

```typescript
type Position = number;

interface TextBuffer {
  readonly length: number;
  insert(position: Position, newText: string): void;
  delete(start: Position, end: Position): void;
  changePosition(position: Position, delta: number): Position;
  findNext(start: Position, query: string): Position | null;
}
```

Контракт цієї адаптації:

- Позиція — цілий індекс від `0` до `length` включно; `length` позначає кінець тексту.
- Для простоти індекси й зміщення рахуються в кодових одиницях UTF-16, як `string.length` у JavaScript. Переноси рядка входять до тексту й не потребують окремої обробки клієнтом.
- `delete(start, end)` видаляє `[start, end)`; порожній діапазон нічого не змінює.
- `changePosition` обмежує результат межами `0…length`.
- `insert` і `delete` відхиляють некоректні позиції; `delete` також відхиляє `start > end`.
- `findNext` шукає непорожній рядок від `start` включно; якщо збігу немає, повертає `null`.

`Position` тут — псевдонім `number`, тому TypeScript сам не перевіряє допустимість позицій. Це відповідальність реалізації. Для повноцінного редактора видалення видимого символу потребуватиме врахування графем: наведене зміщення на `1` може розділити emoji. Приклади нижче використовують ASCII, щоб зосередитися на межах модулів.

### 3. Поведінка клавіш залишається в UI

```typescript
function handleDelete(text: TextBuffer, cursor: Position): Position {
  text.delete(cursor, text.changePosition(cursor, 1));
  return cursor;
}

function handleBackspace(text: TextBuffer, cursor: Position): Position {
  const start = text.changePosition(cursor, -1);
  text.delete(start, cursor);
  return start;
}

function removeSelection(
  text: TextBuffer,
  anchor: Position,
  focus: Position,
): Position {
  const start = Math.min(anchor, focus);
  const end = Math.max(anchor, focus);
  text.delete(start, end);
  return start;
}
```

Це окремі обробники UI, а не методи текстового класу. Вони повертають нову позицію курсора, яку зберігає UI. `anchor` — початок виділення, `focus` — його рухомий край; нормалізація дозволяє виділяти текст у будь-якому напрямку. Обробники Delete і Backspace тут розглядають випадок без активного виділення.

Наприклад, для `ab|cd`, де `|` позначає курсор, Delete дає `ab|d`, а Backspace — `a|cd`. На початку тексту Backspace видаляє порожній діапазон, так само як Delete у кінці. Клас тексту не знає ні про клавіші, ні про виділення.

### 4. Той самий API працює без редактора

```typescript
function replaceAll(
  text: TextBuffer,
  query: string,
  replacement: string,
): number {
  if (query.length === 0) {
    throw new Error("Рядок пошуку має бути непорожнім");
  }

  let position: Position = 0;
  let count = 0;

  while (true) {
    const start = text.findNext(position, query);
    if (start === null) return count;

    const end = text.changePosition(start, query.length);
    text.delete(start, end);
    text.insert(start, replacement);

    // Продовжуємо після вставленого тексту, не замінюючи його повторно.
    position = text.changePosition(start, replacement.length);
    count += 1;
  }
}
```

Функція замінює неперекривні входження зліва направо. Наприклад, `cat cat` після заміни `cat` на `cats` стане `cats cats`, а результатом буде `2`. Пошук продовжується після вставки, тому наявність `cat` усередині `cats` не створює нескінченної заміни. Для порожньої заміни позиція не просувається, але текст скорочується.

Цикл тут перебирає збіги — це робота клієнта. Вставлення й видалення цілих діапазонів виконує модуль тексту. Для цього сценарію не потрібні `Cursor`, `EditorSelection` чи нові методи під пакетну обробку.

^aphsd-ch06-typescript-examples

## Практичні правила

- Формулюйте операції мовою відповідальності модуля: «видалити діапазон тексту», а не «натиснути Backspace».
- Залишайте рішення про дії користувача в модулі інтерфейсу користувача.
- Оцінюйте простоту разом із кодом виклику: короткий API не допомагає, якщо клієнт мусить виконувати всю роботу сам.
- Не скорочуйте число методів ціною складного набору прапорців і параметрів.
- Додавайте потрібні сьогодні можливості; узагальнюйте спосіб їх використання без прогнозування всіх майбутніх задач.

## Важлива цитата

> “the module’s functionality should reflect your current needs, but its interface should not.”

^aphsd-ch06-quote

Зміст: сьогоднішні вимоги визначають можливості модуля, проте API не слід прив’язувати до єдиного способу їх застосування.
