# Декоратор додає поведінку через обгортання

## Визначення

**Декоратор — об’єкт, що приймає інший об’єкт зі спільним інтерфейсом, додає поведінку та делегує йому основну роботу.** Клієнт використовує той самий контракт і може працювати як із базовим об’єктом, так і з обгорнутим.

^decorator-definition

Наприклад, відправник повідомлень знає, як їх доставляти. Декоратор може додавати префікс або записувати факт виклику в журнал. Сам механізм доставки залишається у відправнику.

## Як проходить виклик

```mermaid
flowchart LR
    Client["Клієнт"] -->|"send(message)"| Prefix["PrefixSender<br/>додає префікс"]
    Prefix -->|"send(prefix + message)"| Logging["LoggingSender<br/>записує виклик"]
    Logging -->|"send(message)"| Base["ConsoleSender<br/>виводить повідомлення"]
```

Усі три об’єкти реалізують `Sender`. Декоратор **містить посилання на `Sender`**, тому може обгорнути як базовий об’єкт, так і інший декоратор. Для цього не потрібне успадкування від `ConsoleSender`.

## Приклад 1. Базовий об’єкт і два декоратори

Це власний навчальний приклад до ідеї з розділу 7, а не код із книги. Доставка тут замінена виведенням у консоль, щоб приклад можна було виконати без сервера.

```typescript
interface Sender {
  send(message: string): void;
}

class ConsoleSender implements Sender {
  send(message: string): void {
    console.log(`Доставка: ${message}`);
  }
}

class PrefixSender implements Sender {
  constructor(
    private readonly inner: Sender,
    private readonly prefix: string,
  ) {}

  send(message: string): void {
    this.inner.send(this.prefix + message);
  }
}

class LoggingSender implements Sender {
  constructor(
    private readonly inner: Sender,
    private readonly log: (event: string) => void,
  ) {}

  send(message: string): void {
    this.log(`Виклик send: ${message}`);
    this.inner.send(message);
  }
}

const sender: Sender = new PrefixSender(
  new LoggingSender(new ConsoleSender(), console.log),
  "[Навчання] ",
);

sender.send("Привіт");
// Виклик send: [Навчання] Привіт
// Доставка: [Навчання] Привіт
```

`PrefixSender` змінює повідомлення перед передачею. `LoggingSender` виконує додаткову дію перед делегуванням. `ConsoleSender` завершує ланцюжок. Клієнт викликає лише `send` і не координує ці кроки самостійно.

`implements Sender` перевіряє відповідність класу контракту, але не додає реалізацію методів і не створює успадкування. Детальніше: [TypeScript Handbook — implements](https://www.typescriptlang.org/docs/handbook/2/classes.html#implements-clauses).

> [!note] Контракт прикладу
> `send` приймає текст, до якого дозволено додавати префікс. Якщо контракт обіцяє доставляти точні незмінені байти, `PrefixSender` порушував би його. Журнал фіксує спробу виклику, а не підтверджену доставку. Якщо `log` кидає помилку, делегування не відбудеться — це також частина поведінки цієї простої реалізації.

^decorator-ts-example

## Приклад 2. Порядок обгорток змінює результат

Цей фрагмент використовує класи з попереднього прикладу, але переставляє декоратори:

```typescript
const reordered: Sender = new LoggingSender(
  new PrefixSender(new ConsoleSender(), "[Навчання] "),
  console.log,
);

reordered.send("Привіт");
// Виклик send: Привіт
// Доставка: [Навчання] Привіт
```

Тепер зовнішній `LoggingSender` бачить початковий текст. У першому прикладі журнал отримував уже змінений текст. Доставка однакова, але спостережувана поведінка системи різна.

Зовнішній декоратор першим отримує виклик. Дії після `inner.send(...)`, якби вони були, виконувалися б на зворотному шляху після завершення внутрішнього виклику. У випадку помилки звичайний код після виклику не виконається; потрібний гарантований завершальний крок слід проєктувати окремо.

## Приклад 3. Обгортка, що не додає роботи

```typescript
class PassThroughSender implements Sender {
  constructor(private readonly inner: Sender) {}

  send(message: string): void {
    this.inner.send(message);
  }
}
```

У показаному прикладі клас не змінює дані, не маршрутизує виклик і не додає поведінки. Клієнт міг би отримати `inner` напряму. Це саме той випадок `pass-through method`, який критикує Ousterhout.

Один корисний метод також не виправдовує автоматично велику обгортку. Якщо інтерфейс має двадцять методів, декоратор може додати поведінку до одного, але потребувати дев’ятнадцяти методів пересилання. Зауваження автора стосується співвідношення користі й ціни всього класу.

## Коли декоратор виправданий

- Розширення потрібне лише частині об’єктів, а базовий клас корисний без нього.
- Є кілька потрібних комбінацій поведінки, які зручно складати з об’єктів.
- Обгортка зберігає очікування клієнта щодо контракту, результатів і помилок.
- Додана робота виправдовує новий клас і знання про порядок обгорток.

Для навчального `Sender` декоратори показують механіку патерну. У реальній програмі, де префікс завжди однаковий і потрібен лише в одному місці, звичайного формування рядка перед викликом може бути достатньо.

## Як це пов’язано з критикою в розділі 7

Однаковий API не робить декоратор автоматично поганим: буферизація, наприклад, справді додає роботу. Проте автор застерігає від окремого поверхневого класу на кожне дрібне розширення.

| Ситуація | Альтернатива, яку варто перевірити |
| --- | --- |
| Можливість природна для базового класу й потрібна більшості клієнтів | Додати її до базового класу |
| Можливість потрібна одному сценарію | Залишити її в коді сценарію |
| Кілька дрібних обгорток завжди працюють разом | Об’єднати їх у глибший декоратор |
| Можливість не потребує перехоплення основних викликів | Створити незалежний компонент |

Ці варіанти — критерії вибору, а не заборона патерну.

## Патерн Decorator і синтаксис @decorator у TypeScript

У цій нотатці **Decorator — спосіб композиції об’єктів**. Наведений код не потребує `@` або спеціальних налаштувань декораторів.

Синтаксис `@decorator` — окремий мовний механізм для налаштування класів і їхніх елементів. Наприклад, декоратор методу може замінити метод функцією, яка додає журналювання. Подібність у додаванні поведінки є, але окремий об’єкт-обгортка зі спільним інтерфейсом при цьому не обов’язково створюється.

TypeScript 5.0 запровадив підтримку нової моделі декораторів; старий режим `experimentalDecorators` має інші правила типізації та генерації коду. Приклади цих двох моделей не слід механічно змішувати. Див. [офіційне пояснення декораторів TypeScript 5.0](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#decorators).
